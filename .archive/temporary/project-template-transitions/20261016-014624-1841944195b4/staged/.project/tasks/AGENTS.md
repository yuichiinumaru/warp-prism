# Task Semantic Contract and Administrative Projection

This installed territorial contract governs Tasks **when they exist**, not all
repository work. Canonical distributable source:
`.opencode/templates/.project/tasks/AGENTS.md`; local installation:
`.project/tasks/AGENTS.md`. Local constraints belong in the preserved
`## Project-Specific Overlay`, not a competing baseline.

## Authority and applicability

The effective root Constitution and explicit current User scope govern this
Task-surface correction. Applicable active law still controls actual permissions,
assurance and effects; contradictory legacy consumers must be exposed rather
than silently treated as migrated. Staged Execution Constitution Rules are
proposal evidence, not authority. This contract grants no task movement, VCS,
publication, profile change or governance release.

Use current Rule10 for authority conflicts and Rule30 for claim-fitted evidence.
Rule41/40/42 remain canonical conditional sources pending their governed successor
release; their older folder-derived assumptions do not override this expressly
authorized correction or the effective root. Do not waive their unrelated safety
floors or claim their merger occurred. Unresolved consequential conflicts block
the affected operation, not unrelated authorized work.

## Task existence and sufficient meaning

A Task is durable execution context where consequential intent/responsibility
must survive time, actors, context loss, meaningful decomposition or risk.
A bounded direct change may use request → action → proportionate verification
without a Task. Work occurrence, repository mutation, size or tool availability
does not itself require a durable file. Tasks need no Story; Stories need no Epic.
No Story/Epic template is redefined here.

Preserve an identifiable authorized outcome, bounded scope/effects, material
constraints and checkable success obligations, with the support/context necessary
for the next responsible actor. Inherit/reference existing request, parent,
interface, design or verified project facts instead of copying their truth.
Meaning, not a heading list, is necessary. A two-line contract can suffice; larger
cross-session work must retain its actual decisions, premises, proof limits and
responsibilities. Unknown material scope or success cannot be filled by guessing.

Inspect existing sources/destinations before mutation. That safety obligation
does not require an always-first inspection checkbox. Preserve identity, origin,
material decisions and historical evidence. Existing numbered, AD/RD and legacy
identities remain interpretable; don't mint collisions, conceal changed intent
inside an old identity or normalize historical records for appearance.

## Directory / lane is a projection

`.project/tasks/` remains the canonical physical Task home. Keep existing lanes:

| Directory | Intended administrative display, when supported by actual facts |
|---|---|
| `00-planning` | Planning or a materialized contract with unresolved prerequisites |
| `01-open` | Work offered for execution |
| `02-doing` | Assigned work underway |
| `03-review` | Work queued for an applicable assessment |
| `04-completed` | Work recorded as closed |

Placement creates **no readiness, review requirement, acceptance, completion,
authority or assurance**. A sound contract misplaced in the tree does not lose
its meaning; a deficient one in the expected directory does not gain validity.
Projection drift should be reported/corrected only by an authorized owner using
the underlying facts. No new states, lane renaming or competing Status store is
introduced. Existing administrative labels cannot override actual support.

## Obligations, acceptance and assurance

Completion means actual contract obligations satisfied with appropriate current
evidence, including relevant runtime/integration behavior where claimed. Preserve
material partiality, unmet conditions, residual limits and effect permissions.
Retirement/supersession is not successful completion. A directory, checkbox,
score, header or passing structural check establishes none of these assertions.

Independent assessment is required only when the actual consequence/contract and
applicable law require it; record/reference that obligation and its judgment when
needed. Appropriate self/parent assurance may suffice otherwise. Authors do not
supply required independent acceptance of their own materially affected claims.
No universal Engineer → Expert → Reviewer → 100 pipeline, report, journal or
Attestation follows. Review methods/actor rights remain with their active owners,
not the lane name. Never move a Task or publish merely from an observed PASS.

## Causal dependencies and contract evolution

Represent a material reliance in its consumer's existing context: the interface,
behavior or decision/version needed by the next action, with appropriate support.
Construction may proceed on A's established API contract; integration waits for
its relevant functioning implementation; publication needs combined proof and
separate authority. Whole-upstream-Task waiting is appropriate only when the whole
outcome is genuinely required. Missing dependency records do not prove independence.
This introduces no Claim registry, reliance engine or builder-loop reform.

Workers may challenge a material premise with evidence, not silently amend it.
The smallest competent authorized owner decides changes within grant. Preserve
material amendment authority, prior meaning and affected proof/reliance as needed;
unrelated work can continue. Existing journals, revision counters or amendment
sections remain valid selected encodings, not universal fields or empty sections.
Don't rewrite old journals, reset provenance or duplicate a shared contract.

## Conditional milestone and optional representation

Preserve milestone linkage when active project governance exists **and** the work
materially advances, blocks or verifies it. Reference the real milestone and useful
relationship; do not invent one for ordinary bounded work. Milestone state does
not move Tasks or authorize publication. No new milestone registry is introduced.

Priority/Type, rationale, risk, Story/Epic links, dependency tables, subtasks,
Where/How, named evidence/review sections and journals are available representations.
Include only what carries consequential meaning. Omit inapplicable sections;
don't fill them with N/A/None to satisfy shape. A genuinely applicable requirement
cannot be omitted merely because its heading is optional.

## Source, validation and history boundaries

The distributed Task template is
`.opencode/templates/.project/tasks/000-template.md`; installation uses the existing
template owner and preserves local overlays/prior bytes. Missing/unreadable source
is a real gap, not permission to obtain another project's private `.project/`.
No direct work must install a template just to exist.

The Task artifact validator at
`.opencode/skills/project-development/scripts/validate_task_artifacts.py` owns
deterministic Task checks; the harness validator's Task branch delegates to it.
Both inspect canonical `.project/tasks`, distinguish hard structure from semantic
review, and never prove acceptance from heading or folder. Empty scans cannot
claim corpus PASS. Semantic sufficiency, necessary reliance/evidence and judgment
applicability require bounded primary-source review where code cannot establish
them; no LLM validator or universal metadata form is introduced.

Generated tasklist/UI is owner-generated discovery, not permission or semantic
truth; do not hand-edit it. Cognitive continuity belongs to ai-memory, actual
execution facts to their contract/evidence owner. Preserve existing Tasks,
journals, completed records and history; no mass rewrite, backfill or moves.
