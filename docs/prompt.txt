You are building a Flutter application prototype called **ASW Observatory**.

The app is a **desktop-first, read-only observability console** for an agentic project workspace. It visualizes a mocked Agent System Workspace containing agents, skills, workflows, tasks, and changelog entries.

You do **not** have access to my real files and you must not ask for them. Instead, create a realistic mock workspace inside the project and build the app around that mock data.

## Non-negotiable execution rule

Before building the actual frontend screens, you must first create a complete **Atomic Design System in Flutter**, then use that design system to build every screen.

Do not hardcode visual styles directly in feature screens. Feature screens must compose tokens, atoms, molecules, organisms, templates, and pages from the design system.

## Visual direction

Look and feel: **ultradark obsidian glass**, with subtle **5% hacker** and **5% protoss** influence.

Interpret this as:

* near-black obsidian background
* glass-like dark panels, but not excessive blur
* subtle cyan/violet/gold energy accents
* thin luminous borders
* precise typography
* dense but readable information architecture
* futuristic, serious, command-center feel
* no childish neon overload
* no generic SaaS pastel dashboard
* no Material default look without customization

Accessibility remains mandatory: readable contrast, keyboard-friendly navigation, visible focus states, and clear semantic status colors.

## Product concept

Build one unified system with four top-level areas:

1. **Map** — what exists and how assets relate.
2. **Operate** — active tasks, lanes, review state, blockers.
3. **History** — changelog timeline and change stories.
4. **Governance** — canonical/generated/archive/provenance/staleness visibility.

The app should show two connected domains:

### A. Harness visibility

Read mocked `.opencode/` data:

```text
.opencode/
  agents/
  skills/
  workflows/
```

Show:

* agents
* skills
* super-skills
* sub-skills
* skill-local workflows
* global workflows
* scripts/references/assets attached to skills
* inter-references between agents, skills, workflows, tasks, and changelog entries

### B. Execution visibility

Read mocked `docs/` data:

```text
docs/
  tasks/
    00-planning/
    01-open/
    02-doing/
    03-review/
    04-completed/
  changelog/
```

Show:

* task lanes
* task detail pages
* changelog timeline
* evidence/readiness/proof status
* links between changelog entries and tasks
* links between tasks and skills/workflows

## Domain model

Model everything as graphable assets.

Create a normalized model similar to:

```dart
enum AssetKind {
  agent,
  skill,
  subskill,
  workflow,
  task,
  changelog,
  script,
  reference,
  rule,
}

enum EdgeKind {
  contains,
  routesTo,
  dependsOn,
  references,
  changedBy,
  proves,
  uses,
}

enum Canonicality {
  parentCanonical,
  childLocal,
  generated,
  appendOnly,
  archive,
  mock,
}

class WorkspaceAsset {
  final String id;
  final AssetKind kind;
  final String name;
  final String path;
  final String description;
  final Canonicality canonicality;
  final Map<String, dynamic> frontmatter;
  final List<String> tags;
  final List<String> triggers;
  final List<WorkspaceEdge> edges;
}
```

Adapt as needed, but keep the idea: one normalized graph backbone powers all screens.

## UX requirements

The app should help users understand:

1. What exists.
2. What matters right now.
3. Why something changed.
4. What is blocked, stale, orphaned, or risky.
5. How agents, skills, workflows, tasks, and changelog entries connect.

Use data storytelling, not just tables.

Examples:

* “This review queue is dominated by code-quality and project-management tasks.”
* “These workflows are global but may belong inside a skill-local workflow folder.”
* “This skill has many incoming references and should be treated as governance-critical.”
* “This changelog entry changed a skill used by three active tasks.”
